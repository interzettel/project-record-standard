## Scope and semantic resolutions

### One owner per feature

PRS retains its current runtime, adapters and rendering pipeline. #13 owns the readable index and semantic views of declared JSON. #11 owns specialized dependency calculations and graph interaction. Both can share source links, privacy checks and accessible work tables. Neither issue justifies a second ledger, generic publisher or mandatory schema replacement.

#9 owns record semantics at the consumer boundary. Qurultai owns coordination and room/task delivery; Hermes owns its client and real-worker gates. A passing PRS fixture cannot certify those runtimes.

### Versioning

The [owner correction on #2](https://github.com/interzettel/project-record-standard/issues/2#issuecomment-6424739697) controls the interpretation: one cooperating package has one suite version by default. Independently published modules may use separate versions. The original per-skill proposal is superseded on that point.

#10 owns semantic migration and receipts. [Hermes #38](https://github.com/interzettel/personal-agent-stack/issues/38) owns release discovery and notification. PRS major/minor changes trigger a recorded host-specific assessment; applying an upgrade remains a separately authorized change. Hypothetical v0.5.0 fixtures must remain labelled synthetic.

### Dependency calculations

#11's suggested formulas are proposals, not additions to contract 0.2.0:

- Required, retained, support and raw counts need explicit membership and exclusions. Cancelled items cannot silently enter successful-delivery accounting.
- Accepted-milestone calculations must evaluate each milestone's declared rule. Counting only `sourceAccepted: true` would miss the existing `all-gate-items` rules.
- A completed implementation with an unmet later acceptance gate is not automatically inconsistent. #6 distinguishes execution prerequisites from acceptance gates. A diagnostic can report a contradiction only against a declared dependency meaning; unknown meaning stays unknown.
- A derived “dependency-consistent” ratio is a separately named diagnostic. It cannot overwrite historical Done claims or the canonical progress fraction.
- Readiness requires more than completed prerequisites: explicit holds, source workflow, authority, missing evidence and unknown observations remain visible. Structural impact cannot supply durations or a critical-path schedule.

The maintainer recommendation is an **optional profile using the current PRS runtime**, with a companion contract only if fixtures demonstrate a genuine gap. The extraction decision remains subject to review under #11. ZOMBIEEE supplies implementation evidence, not a competing PRS schema.

### Branding and publication

#12 owns portable convention references and release/documentation semantics. [Zettlerei #88](https://github.com/interzettel/zettlerei-studio/issues/88) owns brand tokens, typography and editorial examples. [Hermes #41](https://github.com/interzettel/personal-agent-stack/issues/41) owns evidence-backed scouting and upstream proposals. A missing brand profile does not block PRS record tooling or a neutral fixture.

#8 standardizes snapshot identity and reference semantics only. Printer recipes and physical delivery belong to Workshop/Hermes. #7 audits only approved public material; private inspector output from #13 is excluded.
